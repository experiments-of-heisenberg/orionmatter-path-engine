## On unknown keys inside Profile/Goal

Confirmed stripped, not rejected: the request succeeds and `parsed.data.profile` contains only known fields. Not an injection risk — stripped keys never reach the engine. The only cost is ergonomic: a client typo nested inside `profile`/`goal`/`constraints` is silently dropped while a top-level typo 400s, so a client bug there is harder to spot.

## Bug hunt (nothing fixed, no failing tests written)

1. **Bug, verified: `src/lib/api/client.ts` cannot be bundled for the browser.** Chain: [client.ts](/agent/workspace/orionmatter-path-engine/src/lib/api/client.ts:9) → `sse.ts` → [errors.ts](/agent/workspace/orionmatter-path-engine/src/lib/api/errors.ts:10) → `../model`, `../intake`, `../privacy`, `../whatif` barrels → [fixtures.ts](/agent/workspace/orionmatter-path-engine/src/lib/model/fixtures.ts:13) (`node:crypto`, `node:fs/promises`, `node:path`) and [ledger.ts](/agent/workspace/orionmatter-path-engine/src/lib/tools/ledger.ts:10) (`node:crypto`). Concrete: `npx esbuild` with `--platform=browser` on an entry importing `postJson` fails with unresolvable `node:*` imports (I ran this). Fix: import error classes from leaf modules (e.g. `../model/errors`, dependency-free agent error modules) instead of barrels, and add a browser-platform bundle check.
2. **Doubt: AbortError portability**, [client.ts](/agent/workspace/orionmatter-path-engine/src/lib/api/client.ts:94) and :138. `instanceof DOMException` misses plain-`Error` aborts (node-fetch style). Concrete: `fetch: () => Promise.reject(Object.assign(new Error("x"), { name: "AbortError" }))` yields `network` instead of rethrowing. Fix: also accept `error instanceof Error && error.name === "AbortError"`.
3. **Doubt: API limits wider than agent caps** (safe — agents re-check first with no model call spent — but the error arrives later without field `issues`): message 2000 vs 500 ([schemas.ts](/agent/workspace/orionmatter-path-engine/src/lib/api/schemas.ts:64) vs `whatif/interpret.ts:37`); privacy text 3500 vs 3000 (`assess.ts:31`); intake text 7000 vs 6000. E.g. a 600-char whatif message passes the schema then fails in the agent. Fix: align the schema maxima with the agent caps.
4. **Doubt: `addSkills` uncapped**, [schemas.ts](/agent/workspace/orionmatter-path-engine/src/lib/schemas.ts:73) (`z.array(z.string())`, no count/length cap) vs `MAX_SKILLS = 5` in `whatif/apply.ts:19`. A 64 KB explore body can carry ~10k skills → ~30k `skillStats` calls on the un-gated light route. Fix: cap count and entry length in `Constraints` or the API schemas.
5. **Doubt: unmapped model errors** in [errors.ts](/agent/workspace/orionmatter-path-engine/src/lib/api/errors.ts:95): `ModelProtocolError` and `ModelEmptyResponseError` fall through to generic `internal` 500; the former fits `model_unreadable` 502. Fix: add branches.
6. **Doubt: BOM tolerated**, [body.ts](/agent/workspace/orionmatter-path-engine/src/lib/api/body.ts:44). `TextDecoder` strips a leading BOM before `JSON.parse`, so `"\uFEFF{...valid...}"` returns 200 (pinned by my test), contrary to the "fails on a BOM" expectation. RFC 8259 permits this, so likely fine — flagged for awareness.
7. **Doubt: no SSE backpressure**, [sse.ts](/agent/workspace/orionmatter-path-engine/src/lib/sse.ts) (`write()` never checks `desiredSize`); a connected-but-idle consumer lets one run buffer unboundedly. Mitigated by the ≤6-run gate.
